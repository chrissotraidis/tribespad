## Change to the working loop

The unit of progress is an integrated launch or gameplay boundary. Individual instruction tests establish a component contract; their count is not playable progress. Do not spend a separate all-platform goal cycle on every ordinary instruction when the same ARM64 implementation can be checked on the host and tested together at the next integrated simulator boundary.

1. Maintain an explicit, source-bound list of remaining DLL translation and module-integration gaps. Enumerate the full image rather than repeatedly discovering only the first missing mnemonic. Include structural code/data and relocation failures, not just opcodes.
2. Batch related blocking instruction families and reuse verified math cores. Keep meaningful independent arithmetic/alias/memory/status checks; preserve fail-closed production behavior. A diagnostic trap census must never become a playable build input.
3. Complete the selected native module/address/patch route and immediately exercise original startup. Bind known services into a reusable runtime shared by the Apple host and the CLI diagnostic. Avoid implementing unrelated compatibility APIs merely because they appear in a library census.
4. Link the real engine/runtime into the Apple app. Establish the main-thread window/presentation path and engine execution lifecycle. Report the actual last original call and observable result on each launch.
5. Test one simulator at a time at integrated boundaries: macOS first for debugging, then iPad, then iPhone. Physical iPad remains the primary acceptance target. A simulator CLI test does not establish UIKit integration or physical behavior.
