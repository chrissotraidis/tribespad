# Launcher: choosing Starsiege: Tribes or Tribes 2

Design research, 24 October 2026. Line numbers refer to `main` at fa8f674. Status labels: Verified (checked), Estimate (judgement, untested), Unknown (not checked). The Starsiege engine work itself is planned in [STARSIEGE-TRIBES-PLAN.md](STARSIEGE-TRIBES-PLAN.md).

## Decision summary
1. The picker runs inside enter_engine before any engine or SDL video starts. Choosing a game launches that engine and nothing else. To change games, the player uses Switch Game, the game quits normally, and the next launch skips the picker and opens the chosen game.
2. The design is a split scene: two tall panels separated by a diagonal seam. Their art comes from the player's own game files, extracted when the player builds the app. When no game art exists, original TribesPad art is used. The motion is a parallax tilt, a slow pan across the art, and jet-trail particles. Each panel shows live player counts.
3. A per-game profile table replaces the Tribes 2 keys hard-coded in mobile_controls.m and mobile_controls.c.
4. TribesPad stays one app, and Starsiege is an optional component of the build. The picker exists only when two engines are bundled.
5. **Revised 24 October:** the picker ships now, at Chris's request, with Starsiege shown as "In development". The card opens this plan instead of a game, and the gear menu's **Open Tribes 2 Directly** removes the extra tap for players who only want Tribes 2. Starsiege then moves through the card states in section 5 as each gate passes. The earlier advice, to ship nothing visible before G6, is superseded.

## 1. iOS lifecycle (Verified unless marked)
- main() at mobile_engine_main.m:145-153 calls tribes_sdl_run_application (sdl_main.c:25-29), which calls SDL_RunApp. SDL calls application_main (sdl_main.c:10-24) on the main thread, and that calls enter_engine (mobile_engine_main.m:19-37) → tb_mobile_prepare_paths (:29) → tb_mobile_controls_install (:35) → tribes_mobile_engine_main (:36).
- The engine runs on the main thread. guest_sdl_backend.c:399-401 stops unless pthread_main_np holds, and :415-421 aborts SDL video init off the main thread or before application_ready. After the engine returns, :403-411 stops if any SDL window, context, audio device or other object is still alive. One engine per process is enforced, and the guest address space cannot be re-entered.
- **Picker (Estimate):** a new port/apple/launcher.m provides "TBGame tb_launcher_choose(void)". At the top of enter_engine, before line 22, it creates a UIWindow attached to tb_window_scene (mobile_engine_main.m:47; the scene adoption at :45-67 already handles windows created outside a scene). It makes that window key and spins CFRunLoopRunInMode(kCFRunLoopDefaultMode,0.05,true) until the player picks a game. It then fades the window out, sets the window to nil, and returns. enter_engine then chooses the storage root and the entry point (tribes_mobile_engine_main or a new starsiege_mobile_engine_main). The picker uses UIKit only, never SDL, so the guest's later SDL_Init is unaffected.
- **Skipping the picker:** NSUserDefaults keys TribesPad.lastGame and TribesPad.nextGame. nextGame is a one-shot value set by Switch Game: it is consumed at launch and the picker is skipped. A Settings row "Show game picker at launch" defaults to on. Home Screen quick actions ("Play Tribes 2" / "Play Starsiege: Tribes", through UIApplicationShortcutItems, read from the scene connection options in TBSceneDelegate :56-61) can skip the picker too. This last point comes from my own knowledge of UIKit; the search for it did not run.
- **Switch Game:** a menu item opens a confirmation ("TribesPad will close. Open it again to play Starsiege: Tribes."), sets nextGame, and then asks the game to quit through its own Quit path. The request-file channel already exists on the codex/find-a-game branch (mobile_controls.m:879-891, prefs/tribespad-request.txt) and needs one new "quit" request. The original Quit exits with code 0 (HANDOFF.md:45), so this is the game's own shutdown and not a raw exit(0).
- **App Store vs sideloading:** Apple's QA1561 says iOS has no public API for quitting an app and not to call exit(), because the app looks like it crashed and may be rejected (https://stackoverflow.com/questions/355168/proper-way-to-exit-iphone-application/18849231, quoting QA1561; https://developer.apple.com/forums/thread/768019). TribesPad has no public binaries (padmint.json:111-114), and every player builds a personal sideloaded copy, so this is acceptable. A future App Store build would have to replace this step with "press Home, then reopen".
- **Other ports:** ScummVM has an in-process "Return to Launcher" (https://docs.scummvm.org/en/latest/use_scummvm/the_launcher.html), but its engines are designed to unload; TribesPad's are not. The libretro docs and guidance note that RetroArch on iOS may need a full quit and reopen when switching cores (https://docs.libretro.com/guides/install-ios/). TribesPad follows the RetroArch model.
- **Mac:** macos_engine_launcher.c:11-25 already execv's a separate TribesPadEngine. A Mac picker can exec either TribesPadEngine or StarsiegeEngine, and Switch Game can relaunch the app. On the Mac, the two engines never need to share a binary (Estimate).
- **Per-game folders:** Tribes 2 stays at Application Support/TribesPad/{Game,Capture,Volume} (mobile_game_paths.m:17-21), so nothing migrates. Starsiege gets TribesPad/Starsiege/{Game,Capture,Volume}. Hard-coded Tribes 2 paths to change: mobile_controls.m:441, :645, :872, and the request path on find-a-game (:890).

## 2. Visual design
- **Layout:** landscape only (UISupportedInterfaceOrientations, Verified). Starsiege on the left and Tribes 2 on the right (plan line 5). The panels are split by an 8-degree diagonal seam drawn with a CAShapeLayer mask. The focused panel widens to 58% with a spring animation. The TribesPad name sits small at the top center, Settings in the corner, and a large "PLAY" on the focused panel.
- **iPad:** each panel holds a title, the art, and two lines of live information: "48 people playing now · 5 servers" and "Game night Sat 9:30 PM ET · in 23 h".
- **iPhone** (compact vertical size class, matching mobile_controls.m:901): the same split with the title and one line of information. Keep 44 pt minimum tap targets and respect the safe areas around the Dynamic Island.
- **Art (Verified, as built):** each card shows its game's own title screen, extracted at build time by scripts/launcher_art.py with the pinned REWise and cached in generated/launcher-art/. Tribes 2: MAINDIR/Art/InstallScreen.Background.bmp from the player's tribes2gsi.exe (640×480). Starsiege: BrightLogo.bmp from MAINDIR/Install/Tribes/base/Shell.vol in the 2004 freeware tribes_gsi.exe (SHA-256 d91ac445…fbb4a4), an 8-bit Phoenix bitmap drawn with the Shell.ppl palette (640×480). The script reads the Darkstar PVOL archive and the PL98 palette itself, with no extra tools. Nothing from either game is committed. **Fallbacks:** Tribes 2 uses bg_Starwolf.png from the player's textures.vl2; Starsiege uses the TribesPad emblem when neither its 1.41 data nor the freeware installer is present. With 1.41 as the target (24 October), the same title screen comes from base/Shell.zip's BrightLogo.png in the 1.41 download, already a PNG.
- **Motion:** UIInterpolatingMotionEffect parallax (art ±18 pt, text ±6 pt), a 30 s pan across the art, and CAEmitterLayer jet trails crossing the seam. Reduce Motion turns all of these off and leaves still art with fades.
- **Live data (Verified, 2026-10-24 02:20 UTC = Fri 22:20 EDT):** list.json had 35 servers, 213 players, and 165 bots, so 48 people (people = num_players − num_bots), with 34 on DAD TRIBES. The Tribes 1 masters (t1query protocol, run from a /tmp copy) listed 30 servers with 15 players on 5 of them, 7 of those on Rosco's Mixtape (base). The fetch path: Tribes 2 over HTTPS with a 120 s cache. For Tribes 1, a native C port of the master and GameSpy queries in t1query.py goes in port/apple/t1_live.c, which can reuse the UDP fan-out pattern of find-a-game's live_servers.m. Game nights (Wed 9 PM, Sat 9:30 PM, every other Sun 9:30 PM ET) come from COMMUNITY-RESEARCH.md:29, whose source is stale (:50), so they should live in a TribesPad-hosted schedule file. For Tribes 1, "pubs start around 8pm ET on Rosco's Mixtape" (plan :90). When offline, show "Offline · last seen 48 people at 10:20 PM".
- **Input:** controller left/right or d-pad changes focus, A plays, the Menu button opens Settings. Keyboard: arrow keys, Tab, Return, and the 1 and 2 keys. Touch: tap a panel to focus it and tap again to play. A press filter already exists (mobile_engine_main.m:68-83), and the picker window handles its own presses.
- **Accessibility:** each panel is a single element, for example "Tribes 2. 48 people playing now. Next game night Saturday 9:30 PM. Button." Live counts are announced politely. Dynamic Type applies to the information lines. Text sits on a scrim so contrast stays at least 4.5:1.

## 3. Shared controls: per-game profile
Add a typedef struct TBGameProfile and choose the profile once at engine start. It replaces these Tribes 2-specific lines:
- emit keys at mobile_controls.c:11-13 (E/D/S/F for movement, then Space, G, W, R, keypad Enter: Tribes 2 movement uses ESDF). Tribes 1 uses W/A/S/D, Space, G, Q, P and I (plan :170-172).
- the button spec at mobile_controls.m:411-420
- the state file at :441 and :645 (Tribes 1 needs its own autoexec hook, plan :172)
- the controller map at :539-561, including zoom on A (:548) and mine on B (:560)
- the menu actions at :744-762
- the hint at :673 and the guides at :842-860
- About at :872-874
- the Online settings text at :214 and :225

Fields: name, storageRoot, moveKeys[4], actionKeys[TB*], buttons[], padMap[], menuGroups[], chat/console/scores keys, stateFile, requestFile, hint text and guide text. Layout, the stick, aim, the trackpad, Settings and release-on-background stay shared. The Tribes 2 table must produce identical events, checked by replaying the existing touch route.

## 4. One app or two
- **Verified:** the Tribes 2 device binary is 65,950,544 bytes (__TEXT 48.5 MB, __text 43.0 MB, __LINKEDIT 11.7 MB). GameData is 662 MB, of which the profile is 644 MB, and the app is 736 MB.
- **Estimate:** Tribes 1 code is 46% of Tribes 2's lifted .text (plan :99). The 36.5 MB figure is an -O0 object and overstates the linked size, so the expected addition is about 20-30 MB of binary and about 160 MB of data (the 1.8 tree is 158 MB). That gives an app of about 0.95 GB. Code pages load lazily, so resident memory should barely change; measure it anyway.
- **Risks:** lifted symbol names and the runtime's single-instance tables (bindings, module catalog) would collide, so each engine needs a prefix and its own table. The guest memory reservation must happen lazily, never in static initializers.
- **Recommendation:** one app, built with "build-tribespad.sh --games tribes2[,starsiege]", where Tribes 2 is the default and Starsiege is opt-in. A Starsiege failure must never block a Tribes 2 build. PadMint: add a second official-download input description, raise disk_gb from 40 to about 55 (Estimate), and make the player-check run both configurations. Whether PadMint's schema supports a build option is Unknown; if it does not, use a second recipe, tribespad-starsiege, that produces the combined app.

## 5. Staged plan: bringing Starsiege into the picker
The picker is built; Starsiege enters it one card state at a time. Each stage names the gate in [STARSIEGE-TRIBES-PLAN.md](STARSIEGE-TRIBES-PLAN.md) that unlocks it and what has to be true before the card changes. A Tribes 2 build without Starsiege never changes behavior, and a Starsiege failure never blocks a Tribes 2 build.

| Stage | Unlocked by | Starsiege card says | Tapping it |
|---|---|---|---|
| P0 (built, draft PR #25) | Chris's request | In development | Opens this plan |
| P1 | G0, G1 | In development | Opens this plan |
| P2 | G2 on Mac | Dev build · main menu | Starts Starsiege (opt-in builds only) |
| P3 | G3, G4 on a device | Play offline | Bot match on the device |
| P4 | G5 and owner approval | Play · N playing now | Server list and joining |
| P5 | G6 and player-check | Play | Released in both configurations |

- **P0, built:** port/apple/launcher.m runs in enter_engine before either engine starts. Tribes 2 plays, with its live player count from list.json. Starsiege shows its own title art and an amber "In development" label. The gear at the top right has Open Tribes 2 Directly and a GitHub link, and Settings → Display → Game Picker at Launch brings the picker back. Keyboard (arrows, 1 and 2, Return) and controller (D-pad, A) both work. Exit: Chris confirms it on the iPad.
- **P1, invisible groundwork (with G0 and G1):** the per-game profile from section 3 and a storage root passed as a parameter, with Tribes 2 producing identical events in the touch-route replay. Starsiege's input is now the community 1.41 installer (162 MB), pinned in config/starsiege/inputs.json and prepared by scripts/starsiege/prepare-inputs.py (done 24 October). The picker's art step takes BrightLogo.png from its base/Shell.zip, so the freeware installer is no longer needed for the card. Add the TBGame value that launcher.m returns to enter_engine, still always Tribes 2. Exit: a Tribes 2 build plays exactly as before, and a fresh-checkout build shows the Starsiege art.
- **P2, dev builds (G2):** a build option, build-tribespad.sh --games tribes2,starsiege, bundles the Starsiege engine and data under Application Support/TribesPad/Starsiege. In those builds the card reads "Dev build · main menu" and starts it: on the Mac by exec'ing a separate StarsiegeEngine, on iPad through a second entry point. Symbol prefixes and separate runtime tables keep the two engines apart (section 4). The card adds the Tribes 1 population from t1_live.c. Exit: the Starsiege main menu appears on the Mac from the picker, and a default build still shows "In development".
  - **Mac half built (24 October):** the Mac app now opens on the picker too. port/apple/launcher_mac.m is the AppKit twin of launcher.m (same layout, art, focus, gear menu, keyboard and controller) and is the app's executable; it execs the chosen engine, Tribes 2's TribesPadEngine or StarsiegeEngine, both in Contents/MacOS, so each starts in a fresh process. "Open Tribes 2 Directly" skips it. build-tribespad.sh --platform macos --games tribes2,starsiege runs scripts/starsiege/bundle_mac.py, which adds the engine (built at -O1, ANGLE from the app's Contents/Frameworks) and the 1.41 game folder with TribesPad's defaults; the picker copies that folder to Application Support/TribesPad/Starsiege on first launch and whenever the bundled copy changes, keeping the player's config, temp and recordings. Checked headless on this Mac: the bundled picker shows "Dev build" ([snapshot](validation/mac-picker-starsiege-dev-2026-10-24.png)), choosing Starsiege (TRIBESPAD_PICK=starsiege) execs the bundled engine, which loads ANGLE from the app and draws the main menu with its cursor, and a build without Starsiege shows "In development". Still open: a visible run on the Mac (owner's go-ahead), Tribes 2 started through the picker on screen, the iPad entry point.
  - **iPad half built (24 October, same day):** scripts/starsiege/build_engine.py --platform device|simulator compiles the same engine for iOS and links everything, including Starsiege's own copies of TribesPad's runtime and SDL backend, into one relocatable object with ld -r that exports only starsiege_mobile_engine_main. All its other symbols are local, so nothing collides with Tribes 2's copies; SDL, GL4ES, ANGLE, OpenAL and the math libraries stay undefined and resolve against the app's, so the process has one of each (section 4's prefixing, done by the linker). build-tribespad.sh --games tribes2,starsiege passes it to build-ipad-engine.py (--starsiege-object), which links it, defines TB_STARSIEGE and bundles GameData/Starsiege; launcher.m then offers "Dev build" and returns the choice, and enter_engine calls the entry point with paths from port/apple/starsiege_paths.m (shared with the Mac picker). iOS allows one window per display, so every Starsiege window draws into the one SDL window, and content_area.m's new tb_content_fix_game_size makes the game area exactly 800x600, 4:3 and centred, for the system to scale up. A touch moves the game's cursor to the finger and clicks; trackpads and mice stay relative. On the iPad Pro (backup, install and read-back each time, Application Support identical): Starsiege started through TRIBESPAD_PICK=starsiege, drew its main menu ([frame](validation/starsiege-ipad-main-menu-2026-10-24.png)) at about 100 fps, and Tribes 2 still started from the same build. The binary grew from 66 to 99.7 MB and the app to 992 MB. One of the first three launches hung in GL4ES (draw_renderlist) right after the first frame; Starsiege rebuilds its WGL context twice while starting, so starsiege_gl.c now parks a deleted context and reuses it for the next one on the same drawable, after which five launches in a row ran cleanly. Game controllers drive the game's own default controls (starsiege_controller.m: left stick WASD, right stick the mouse, triggers fire and jet, A jump, B crouch, X grenade, Y repair kit, RB next weapon, LB zoom, Menu Escape, View Tab), checked headless with scripted pad input. Both pickers now show the Tribes 1 population on the Starsiege card: port/apple/t1_live.c asks the six community masters (t1m1-3.tribes1.co and t1m1-3.pu.net) and pings every listed server with the game's own query, following the masters' maintainer's t1net-go library; on 24 October at 18:40 JST all six masters answered, 29 servers replied, and 6 people were on 3 of them. Open: touch, controller and the iPad picker card untested by hand; the frame is 800x600 only.
- **P3, offline play (G3 and G4):** a bot match on the iPad with the Tribes 1 control profile, and Switch Game in both games' menus, which quits through the game's own Quit and sets TribesPad.nextGame. The card reads "Play offline". Exit: a full offline match on the iPad and iPhone, with controls checked by touch, controller and keyboard folio.
- **P4, online (G5):** the original server browser with the community masters, read-only first. Joining public servers waits for the owner's explicit approval for Tribes 1. The card shows "Play · N playing now". Exit: approval recorded, and a join tested on a live server.
- **P5, release (G6):** Home Screen quick actions, PadMint's second input description and higher disk estimate, and the player-check run with both configurations. Exit: the player-check passes from a clean checkout with and without Starsiege.

The P0 art step already reads Starsiege's PVOL archives and palettes, so G1's census of the shell bitmaps can reuse scripts/launcher_art.py.
